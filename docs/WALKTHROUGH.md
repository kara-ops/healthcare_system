# Architecture Walkthrough: Django & DRF for the FastAPI + SQLAlchemy Developer

Welcome! If you are an experienced **FastAPI**, **SQLAlchemy**, and **Alembic** developer approaching Django and Django REST Framework (DRF) for the first time, this document was written specifically for you.

Coming from FastAPI, you are accustomed to composing minimal, explicit primitives: Pydantic schemas for data validation, raw SQLAlchemy declarative models, manual `session.commit()` calls, `Depends()` for dependency injection, and Alembic for autogenerated migration revisions.

Django approaches backend engineering with a different philosophy: **"Batteries Included" with cohesive conventions**. Instead of assembling third-party libraries, Django provides an integrated ecosystem where the ORM, authentication system, migrations engine, routing, and administrative interface share a common design language.

This walkthrough breaks down the structure of this project, translates familiar FastAPI patterns into Django conventions, traces an end-to-end request lifecycle, and answers critical architectural questions.

---

## 1. The Rosetta Stone: FastAPI/SQLAlchemy vs. Django/DRF

Here is how the core paradigms translate between the two ecosystems:

| Concept | FastAPI + SQLAlchemy + Alembic | Django + Django REST Framework (DRF) | Key Conceptual Differences |
|---|---|---|---|
| **Data Validation & Parsing** | `pydantic.BaseModel` | `rest_framework.serializers.Serializer` / `ModelSerializer` | Pydantic types validate eagerly on assignment/instantiation; DRF serializers validate explicitly on `.is_valid()`. `ModelSerializer` introspects the ORM model to generate validation rules automatically. |
| **Database Models** | SQLAlchemy `Base` declarative models (`mapped_column`, `relationship`) | `django.db.models.Model` (Active Record pattern) | SQLAlchemy models are decoupled entities managed by an explicit `Session`. Django models follow the Active Record pattern where instances have built-in persistence methods (`.save()`, `.delete()`). |
| **Database Migrations** | `alembic revision --autogenerate`, `alembic upgrade head` | `python manage.py makemigrations`, `python manage.py migrate` | Alembic inspects SQLAlchemy metadata vs DB schemas. Django computes migration diffs in pure Python by comparing model states across versioned migration files before applying them. |
| **Authentication & Dependency Injection** | `Depends(get_current_user)` parameter in route handlers | `rest_framework_simplejwt.authentication.JWTAuthentication` setting `request.user` | FastAPI uses explicit function dependency injection per route. DRF uses a declarative middleware/pipeline configured globally via `DEFAULT_AUTHENTICATION_CLASSES`. |
| **Authorization / Permissions** | Custom `Depends()` check (e.g. `Depends(require_role)`) or manual logic | `rest_framework.permissions.BasePermission` (`has_permission`, `has_object_permission`) | DRF separates view-level access (`has_permission`) from row/instance-level access (`has_object_permission`), evaluated before and during view execution. |
| **Routing & Endpoints** | `APIRouter(prefix="/...")` and `@router.post("/")` | `config/urls.py` + app `urls.py` dispatching to `APIView` / `generics.*` | FastAPI couples route path, HTTP method, and handler function via decorators. Django separates URL dispatching trees from class-based view classes. |
| **Exception Handling** | `@app.exception_handler(HTTPException)` or Starlette handlers | `EXCEPTION_HANDLER` setting pointing to `apps.core.exceptions.custom_exception_handler` | DRF routes all unhandled or API-raised exceptions through a single centralized handler function, allowing uniform JSON response shaping. |
| **Transaction & Session Management** | Explicit `session.begin()`, `session.commit()`, `session.rollback()` | Django ORM auto-commit mode, or explicit `transaction.atomic()` blocks | In Django, every query commits immediately by default unless wrapped in an atomic transaction or view decorator (`@transaction.atomic`). |
| **Admin Interface** | None built-in (often requires SQLAdmin or custom frontend) | Built-in `django.contrib.admin` | Django generates a full-featured, secure CRUD interface for registered models with zero custom frontend code. |
| **Queryset Evaluation** | `db.execute(select(Model).where(...)).scalars().all()` | `Model.objects.filter(...)` | Django querysets are lazy. They are not evaluated against the database until iterated over, sliced, or evaluated in a serializer. |

## 2. Guided Tour: File-by-File & Folder-by-Folder

Unlike a FastAPI application where file layout is completely unconstrained, Django projects follow a disciplined two-tier architecture: the **project root configuration** (`config/`) and modular domain **applications** (`apps/`).

### Root Workspace Files

- **`manage.py`**:
  - *Why it exists*: The command-line management utility for your project.
  - *FastAPI equivalent*: Combining `uvicorn main:app --reload`, `alembic`, and custom CLI scripts into a single entrypoint. It configures `DJANGO_SETTINGS_MODULE` and passes commands to Django's core engine.
- **`requirements.txt`**:
  - *Why it exists*: Declares exact pinned versions of dependencies (Django 5.1, DRF 3.15, SimpleJWT 5.4, psycopg 3, pytest).
- **`.env` & `.env.example`**:
  - *Why it exists*: Secrets and runtime environment parameters parsed by `django-environ`. In FastAPI, you would typically use `pydantic-settings` with a `BaseSettings` class.
- **`docker-compose.yml`**:
  - *Why it exists*: Spawns a production-aligned PostgreSQL 16 container with persistent volume storage (`postgres_data`).
- **`pytest.ini`**:
  - *Why it exists*: Configures the pytest runner, defining `DJANGO_SETTINGS_MODULE = config.settings` so tests boot with Django's loaded application registry.

---

### Project Configuration: `config/`

The `config/` directory serves as the root orchestration module for the entire Django deployment:

- **`config/__init__.py`**:
  - Marks `config` as a Python package.
- **`config/settings.py`**:
  - *FastAPI equivalent*: `app/core/config.py` with `Settings(BaseSettings)`.
  - In Django, `settings.py` is the centralized configuration hub. It defines `INSTALLED_APPS` (app registry), `DATABASES` (engine, credentials), `MIDDLEWARE` (request/response pipeline), `AUTH_USER_MODEL` (custom identity table), and DRF's global behavior (`DEFAULT_PERMISSION_CLASSES = ['IsAuthenticated']`, `DEFAULT_AUTHENTICATION_CLASSES = ['JWTAuthentication']`, `EXCEPTION_HANDLER`).
- **`config/urls.py`**:
  - *FastAPI equivalent*: The root `main.py` where you call `app.include_router(auth_router)`, `app.include_router(patient_router)`, etc.
  - In Django, `config/urls.py` holds `urlpatterns = [...]`, using `path('api/<domain>/', include('apps.<domain>.urls'))` to namespace each domain's routes cleanly.
- **`config/wsgi.py` & `config/asgi.py`**:
  - *FastAPI equivalent*: The ASGI `app = FastAPI()` object exported to Uvicorn.
  - `wsgi.py` is the synchronous web gateway (for Gunicorn/uWSGI). `asgi.py` provides the asynchronous equivalent for ASGI servers like Uvicorn or Daphne.

### Modular Domain Applications: `apps/`

In Django, an **"app"** is a self-contained, pluggable package encapsulating models, views, serializers, admin interfaces, and migrations for a specific bounded context.

#### 1. Core Framework Foundation: `apps/core/`
This app provides system-wide infrastructural components used by all other apps:
- **`apps/core/models.py`**:
  - Declares `TimestampedModel(models.Model)`.
  - *FastAPI/SQLAlchemy equivalent*: An abstract declarative mixin class defining `created_at = Column(DateTime, server_default=func.now())` and `updated_at = Column(DateTime, onupdate=func.now())`. Marking `class Meta: abstract = True` instructs Django not to create a database table for `TimestampedModel` itself, but to inject these fields into inheriting child models (`Patient`, `Doctor`).
- **`apps/core/permissions.py`**:
  - Declares `IsOwner(BasePermission)`.
  - *FastAPI equivalent*: A dependency like `def verify_owner(obj = Depends(get_doctor), user = Depends(get_current_user)): if obj.created_by_id != user.id: raise HTTPException(403)`.
  - In DRF, `IsOwner` overrides `has_object_permission(self, request, view, obj)` and checks `return obj.created_by == request.user`.
- **`apps/core/exceptions.py`**:
  - Declares `custom_exception_handler(exc, context)`.
  - Intercepts all exceptions (DRF `ValidationError`, `AuthenticationFailed`, `PermissionDenied`, `NotFound`, `MethodNotAllowed`, and Django core `Http404`) and maps them to a uniform contract envelope:
    ```json
    { "error": { "code": "...", "message": "...", "details": { ... } } }
    ```
  - Unhandled 500 errors are caught and masked to prevent leaking internal tracebacks to API clients.

#### 2. Authentication & Users: `apps/accounts/`
- **`apps/accounts/models.py`**:
  - Declares custom `User(AbstractBaseUser, PermissionsMixin)`.
  - In Django, the default user model expects a `username` field. By extending `AbstractBaseUser` before initial migrations, we specify `USERNAME_FIELD = 'email'`, add a required `name` string, and eliminate the legacy username field.
- **`apps/accounts/managers.py`**:
  - Declares `CustomUserManager(BaseUserManager)`.
  - Encapsulates low-level user persistence: handles `normalize_email` (converting email domains to lowercase) and securely hashes passwords via `set_password()`.
- **`apps/accounts/serializers.py`**:
  - `RegisterSerializer`: Validates `name`, `email` (uniqueness), and runs raw passwords through Django's 4 built-in password validators (`UserAttributeSimilarityValidator`, `MinimumLengthValidator`, `CommonPasswordValidator`, `NumericPasswordValidator`).
  - `LoginSerializer`: Uses Django's `authenticate(email=..., password=...)` to verify credentials against PBKDF2/argon2 hashes and ensure active account status.
  - `UserSerializer`: Read-only serializer exposing `{id, name, email}`.
- **`apps/accounts/views.py`**:
  - `RegisterView`: Generic `CreateAPIView` with `AllowAny` permission. Returns 201 with created user details.
  - `LoginView`: `APIView` validating credentials and issuing JWT tokens via `RefreshToken.for_user(user)`. Returns `{access, refresh, user}`.
- **`apps/accounts/urls.py`**:
  - Maps `register/`, `login/`, and `token/refresh/` (`TokenRefreshView` from SimpleJWT).

#### 3. Patient Records: `apps/patients/`
- **`apps/patients/models.py`**:
  - `Patient(TimestampedModel)`: Contains demographic fields (`name`, `age` with 1–150 validators, `gender` with choices, `phone`, `address`, `medical_history`) and `created_by = ForeignKey(User, on_delete=models.CASCADE)`.
- **`apps/patients/serializers.py`**:
  - `PatientSerializer`: Validates non-empty whitespace-stripped strings, valid age boundaries, and valid gender enum values.
- **`apps/patients/views.py`**:
  - `PatientListCreateView` & `PatientDetailView`: Subclasses DRF's generic class-based views (`ListCreateAPIView`, `RetrieveUpdateDestroyAPIView`).
  - **Ownership Isolation**: Overrides `get_queryset()` to return `Patient.objects.filter(created_by=self.request.user)`. Because other users' patients are excluded from the queryset, any query for another user's patient ID automatically raises DRF's `NotFound` (`404`), preventing IDOR existence disclosure.

#### 4. Doctor Directory: `apps/doctors/`
- **`apps/doctors/models.py`**:
  - `Doctor(TimestampedModel)`: Models qualified physicians (`name`, `specialization`, `email` with unique constraint, `phone`, `years_of_experience`, and `created_by`).
- **`apps/doctors/serializers.py`**:
  - `DoctorSerializer`: Enforces case-insensitive email uniqueness and non-negative experience.
- **`apps/doctors/views.py`**:
  - `DoctorListCreateView`: Accessible to all authenticated users for reading (`GET`) and creating (`POST`).
  - `DoctorDetailView`: Dynamically determines permissions in `get_permissions()`. Safe HTTP methods (`GET`, `HEAD`, `OPTIONS`) require only `IsAuthenticated`, allowing all users to view any doctor. Modifying methods (`PUT`, `PATCH`, `DELETE`) require `[IsAuthenticated(), IsOwner()]`, returning `403 Permission Denied` if a user attempts to edit a doctor created by someone else.

#### 5. Patient-Doctor Mappings: `apps/mappings/`
- **`apps/mappings/models.py`**:
  - `PatientDoctorMapping(models.Model)`: Relational association entity with `patient = ForeignKey(Patient, on_delete=models.CASCADE)` and `doctor = ForeignKey(Doctor, on_delete=models.CASCADE)`.
  - Enforces database-level uniqueness via `unique_together = ('patient', 'doctor')`.
- **`apps/mappings/serializers.py`**:
  - `MappingCreateSerializer`: Write-only validator accepting `patient_id` and `doctor_id`. Validates that the patient exists AND is owned by the current user (`validate_patient_id`), that the doctor exists (`validate_doctor_id`), and that the assignment is not a duplicate (`validate`).
  - `MappingReadSerializer`: Read-only serializer returning flattened metadata (`id`, `patient_id`, `doctor_id`, `patient_name`, `doctor_name`, `assigned_at`).
- **`apps/mappings/views.py`**:
  - `MappingListCreateView`: `GET` lists mappings for patients owned by the current user using `select_related('patient', 'doctor')` to eliminate N+1 queries. `POST` creates mappings, converting duplicate conflicts into HTTP `400` with code `duplicate_mapping`.
  - `MappingDetailView`: Dual-semantic view sharing `mappings/<int:pk>/`. `GET` treats `pk` as `patient_id` (listing all doctors assigned to that patient). `DELETE` treats `pk` as `mapping_id` (deleting that assignment).
- **`apps/mappings/urls.py`**:
  - Uses explicit URL patterns rather than DRF ViewSet routers, ensuring custom REST semantics without accidental routing collisions.

## 3. End-to-End Request Lifecycle: `POST /api/mappings/`

To understand how Django's execution model works in practice, let's trace a concrete HTTP request through every layer of the system:

```
[ Client HTTP Request: POST /api/mappings/ with Bearer Token & JSON Body ]
                                  │
                                  ▼
                    [ WSGI / ASGI Gateway Layer ]
                                  │
                                  ▼
                    [ Django Middleware Pipeline ]
                     (Security, Sessions, CSRF)
                                  │
                                  ▼
                     [ URL Dispatcher Routing ]
                  (config/urls.py -> apps/mappings/urls.py)
                                  │
                                  ▼
               [ DRF View Handler (as_view() / dispatch) ]
                                  │
                                  ▼
             [ Authentication Phase (JWTAuthentication) ]
               - Parses Authorization: Bearer <token>
               - Validates HMAC / RSA signature & exp
               - Loads User -> sets request.user
                                  │
                                  ▼
              [ Permission Phase (check_permissions) ]
               - Evaluates IsAuthenticated (passes)
                                  │
                                  ▼
              [ Content Negotiation & JSON Parsing ]
               - Parses raw body into request.data dict
                                  │
                                  ▼
               [ View Method: MappingListCreateView.post ]
                                  │
                                  ▼
               [ Serializer Validation: MappingCreateSerializer ]
               - validate_patient_id: Patient exists & owned by user?
                 (If unowned -> raises NotFound -> HTTP 404)
               - validate_doctor_id: Doctor exists?
                 (If missing -> raises ValidationError -> HTTP 400)
               - validate: Duplicate mapping pair?
                 (If duplicate -> returns HTTP 400 duplicate_mapping)
                                  │
                                  ▼
                     [ Database Persistence (Save) ]
               - PatientDoctorMapping.objects.create(...)
               - INSERT INTO mappings_patientdoctormapping ...
               - Psycopg executes query on PostgreSQL
                                  │
                                  ▼
              [ Response Formatting & Serialization ]
               - MappingReadSerializer formats output data
               - Response(read_serializer.data, status=201)
                                  │
                                  ▼
               [ JSON Rendering & HTTP Response Delivery ]
               - JSONRenderer encodes dict to UTF-8 JSON bytes
               - HTTP 201 Created sent over wire to client
```

### Detailed Lifecycle Phases:

1. **HTTP Request Arrival**:
   A client issues `POST http://127.0.0.1:8000/api/mappings/` with header `Authorization: Bearer <access_token>` and JSON body `{"patient_id": 1, "doctor_id": 2}`.
2. **WSGI/ASGI Gateway**:
   The web server (e.g. Gunicorn or Uvicorn) receives the raw TCP socket connection, parses the HTTP stream into standard WSGI environment variables (`environ`), and creates a Django `WSGIRequest` object.
3. **Django Middleware Pipeline**:
   The request traverses global middleware registered in `settings.MIDDLEWARE`:
   - `SecurityMiddleware`: Handles SSL redirection, X-Content-Type-Options.
   - `SessionMiddleware` & `CommonMiddleware`: URL normalization (e.g. appending trailing slashes).
   - `CsrfViewMiddleware`: Evaluates CSRF protection (bypassed by DRF for token-based APIs).
4. **URL Resolution**:
   Django matches the path `/api/mappings/` against `config/urls.py`, which delegates to `apps/mappings/urls.py`. The matching entry is `path('', views.MappingListCreateView.as_view(), name='mapping-list-create')`.
5. **DRF View Initialization**:
   `as_view()` wraps the class-based view. The incoming `HttpRequest` is wrapped into a DRF `Request` instance, which provides lazy parsing of `.data`, `.query_params`, and unified `.user`.
6. **Authentication & Identity Resolution**:
   DRF executes `self.initial(request)`. It iterates through `DEFAULT_AUTHENTICATION_CLASSES`:
   - `JWTAuthentication` extracts the token string from the `Authorization: Bearer <token>` header.
   - It validates the cryptographic signature using `settings.SECRET_KEY` and checks expiration (`exp`).
   - It queries PostgreSQL for the active user (`SELECT * FROM accounts_user WHERE id = <token.user_id>`).
   - The user instance is attached to `request.user`. (If the token is invalid or expired, `AuthenticationFailed` is raised).
7. **Permission Checking**:
   `self.check_permissions(request)` evaluates `IsAuthenticated`. Since `request.user.is_authenticated` is `True`, execution proceeds.
8. **View Execution (`post()` method)**:
   `MappingListCreateView.post(request)` is called. It passes `request.data` and `context={'request': request}` into `MappingCreateSerializer`.
9. **Serializer Validation**:
   `serializer.is_valid()` executes:
   - Field-level `validate_patient_id`: Queries `Patient.objects.filter(id=value).first()`. If the patient is not found OR `patient.created_by != request.user`, it raises a `ValidationError("Patient not found")`. The view intercepts this and raises `NotFound("Patient not found")`, ensuring an HTTP 404 response.
   - Field-level `validate_doctor_id`: Verifies the doctor exists in the database.
   - Object-level `validate`: Checks `PatientDoctorMapping.objects.filter(patient_id=..., doctor_id=...).exists()`. If a duplicate assignment exists, it raises a validation error, which the view returns as an HTTP 400 with code `duplicate_mapping`.
10. **Database Insertion (Active Record Save)**:
    `serializer.save()` triggers `PatientDoctorMapping.objects.create(...)`. The Django ORM translates this into SQL:
    ```sql
    INSERT INTO mappings_patientdoctormapping (patient_id, doctor_id, assigned_at)
    VALUES (1, 2, NOW())
    RETURNING mappings_patientdoctormapping.id, mappings_patientdoctormapping.assigned_at;
    ```
    Psycopg sends the parameterized query to PostgreSQL, which executes it within the auto-committed transaction.
11. **Response Formatting & Serialization**:
    The resulting mapping instance is passed to `MappingReadSerializer`, which reads `patient.name` and `doctor.name` (retrieved via joins/lookups) and returns a clean dictionary.
12. **Content Rendering & Error Envelope**:
    - *Success path*: `Response(read_serializer.data, status=status.HTTP_201_CREATED)` is passed to DRF's `JSONRenderer`, which encodes the dict to JSON bytes and sets `Content-Type: application/json`.
    - *Failure path*: If any step raised an exception (`NotFound`, `ValidationError`, `IntegrityError`), DRF catches it and invokes `apps/core/exceptions.custom_exception_handler`. The handler constructs the uniform `{ "error": { "code": ..., "message": ..., "details": ... } }` payload and attaches the corresponding HTTP status code (400, 401, 404, 500).

## 4. Technical Examiner / Architectural Interview Q&A

### Q1: Why must a custom User model be declared before running the very first database migration in Django?
**Answer**:
Django's built-in models (such as `django.contrib.admin`, `auth`, and session frameworks) establish foreign keys to `AUTH_USER_MODEL`. If the default migration runs first using Django's built-in `auth.User`, foreign key constraints are baked into the database schema pointing to `auth_user`. Changing to a custom user model later requires complex, error-prone schema refactoring across multiple third-party apps. Creating a custom `User(AbstractBaseUser)` upfront in `apps/accounts` and setting `AUTH_USER_MODEL = 'accounts.User'` in `settings.py` before `migrate` ensures all foreign keys across the entire project point directly to our custom user table from day one.

---

### Q2: How does this architecture prevent Insecure Direct Object References (IDOR) on Patient records, and why does an unauthorized request return HTTP 404 instead of HTTP 403?
**Answer**:
In `apps/patients/views.py`, both `PatientListCreateView` and `PatientDetailView` override `get_queryset()`:
```python
def get_queryset(self):
    return Patient.objects.filter(created_by=self.request.user)
```
When a user attempts to retrieve, update, or delete a patient with ID `99` belonging to another user, DRF executes `.get_object()` against the filtered queryset. Because the record is absent from the user-scoped queryset, Django raises `Http404` (`NotFound`). 
Returning `404 Not Found` rather than `403 Forbidden` is a deliberate security decision: `403` informs an attacker that the resource exists (leaking record existence), whereas `404` completely masks existence, treating unauthorized records identically to non-existent ones.

---

### Q3: Why did we avoid DRF's `DefaultRouter` and `ModelViewSet` for the mappings app in favor of explicit `APIView` classes?
**Answer**:
DRF's `DefaultRouter` with a `ModelViewSet` automatically generates standard REST URL routes, specifically binding `GET /api/mappings/<int:pk>/` to `MappingViewSet.retrieve(pk)` (retrieving a mapping by its primary key). 
However, Section 1.1 and Section 2 of our project specification mandate dual semantics for `mappings/<int:pk>/`:
- `GET /api/mappings/<patient_id>/`: Retrieves all doctors assigned to that patient (where `<pk>` is a **patient ID**).
- `DELETE /api/mappings/<id>/`: Deletes a specific assignment (where `<pk>` is a **mapping ID**).

A standard DRF router would silently map `GET /api/mappings/<id>/` to mapping ID lookup, violating the specification. Using an explicit `APIView` (`MappingDetailView`) allows us to inspect the HTTP method within a single endpoint and cleanly execute patient-based lookup for `GET` and mapping-based deletion for `DELETE`.

### Q4: How does Django's transaction handling differ from SQLAlchemy's `Session`, and how would you execute multi-table operations atomically?
**Answer**:
In SQLAlchemy, the `Session` operates as a unit-of-work pattern where modifications remain in memory until `session.commit()` is explicitly called. In Django ORM, the default mode is **auto-commit**: each `.save()`, `.create()`, or `.delete()` call immediately executes and commits an SQL statement to the database.
To run multiple database operations atomically (e.g. creating a patient and automatically creating an initial mapping), Django provides `django.db.transaction.atomic()`:
```python
from django.db import transaction

with transaction.atomic():
    patient = Patient.objects.create(...)
    mapping = PatientDoctorMapping.objects.create(patient=patient, doctor=doctor)
```
If an exception occurs within the `atomic()` block, Django issues an SQL `ROLLBACK` to PostgreSQL, reverting all statements executed within that block.

### Q5: How are N+1 database query bottlenecks eliminated when listing patient-doctor mappings?
**Answer**:
When retrieving mappings, each mapping references both a `Patient` and a `Doctor`. Serializing `patient.name` and `doctor.name` without query optimization would cause an **N+1 query problem**: 1 query to fetch $N$ mappings, followed by $2N$ queries to fetch each related patient and doctor record.
In `apps/mappings/views.py`, we optimize the queryset using `select_related`:
```python
PatientDoctorMapping.objects.filter(patient__created_by=request.user).select_related('patient', 'doctor')
```
Because `patient` and `doctor` are single-valued foreign keys, `select_related` causes the Django ORM to generate an SQL `INNER JOIN` (or `LEFT OUTER JOIN`), fetching all mapping, patient, and doctor columns in a single database roundtrip. For multi-valued relations (many-to-many or reverse foreign keys), `prefetch_related` would be used instead to perform batch lookup queries in Python.

### Q6: How does DRF differentiate between view-level and object-level permissions, and how is this applied in the Doctor endpoints?
**Answer**:
DRF enforces permissions at two distinct stages:
1. **View-Level Permissions (`has_permission`)**: Executed during initial request handling before any database lookup. For example, `IsAuthenticated.has_permission(request, view)` checks `request.user.is_authenticated`. If false, request processing halts with HTTP 401.
2. **Object-Level Permissions (`has_object_permission`)**: Executed inside `get_object()` after the target database record has been fetched.

In `apps/doctors/views.py`, `DoctorDetailView` overrides `get_permissions()`:
```python
def get_permissions(self):
    if self.request.method in permissions.SAFE_METHODS:
        return [permissions.IsAuthenticated()]
    return [permissions.IsAuthenticated(), IsOwner()]
```
For `GET /api/doctors/1/`, only `IsAuthenticated` is active, allowing any logged-in user to read the doctor. For `PUT`, `PATCH`, or `DELETE /api/doctors/1/`, `IsOwner` is active. During `.get_object()`, DRF calls `IsOwner.has_object_permission()`, checking `obj.created_by == request.user`. If another user attempts the update, DRF raises `PermissionDenied` (`403`).

### Q7: What happens to relational integrity when a Patient or Doctor is deleted, and how is cascading handled?
**Answer**:
Both foreign keys in `PatientDoctorMapping` are defined with `on_delete=models.CASCADE`:
```python
class PatientDoctorMapping(models.Model):
    patient = models.ForeignKey(Patient, on_delete=models.CASCADE, related_name='doctor_mappings')
    doctor = models.ForeignKey(Doctor, on_delete=models.CASCADE, related_name='patient_mappings')
```
When `DELETE /api/patients/1/` is executed, Django's ORM queries all dependent records and deletes both the `Patient` row and all corresponding `PatientDoctorMapping` rows. Furthermore, PostgreSQL enforces foreign key constraints at the database engine level (`ON DELETE CASCADE`), ensuring no orphaned mappings can exist in the database even if modifications are executed outside the ORM.

### Q8: How does the custom exception handler ensure consistent JSON error shapes across unexpected server crashes?
**Answer**:
DRF's built-in `exception_handler` only handles exceptions inheriting from `rest_framework.exceptions.APIException` (such as `ValidationError` or `AuthenticationFailed`). Unhandled Python exceptions (e.g. `KeyError`, `ZeroDivisionError`, `DatabaseError`) bypass DRF and trigger Django's default 500 handler, which in debug mode outputs HTML tracebacks or generic server errors.
In `apps/core/exceptions.py`, our `custom_exception_handler(exc, context)`:
1. Converts Django core exceptions (`Http404`, `PermissionDenied`) into DRF equivalents.
2. Calls DRF's standard handler.
3. If DRF returns `None` (indicating an unhandled exception), our handler catches it and constructs an explicit `Response` with HTTP `500 Internal Server Error`:
   ```python
   Response({
       "error": {
           "code": "server_error",
           "message": "An unexpected error occurred.",
           "details": {}
       }
   }, status=status.HTTP_500_INTERNAL_SERVER_ERROR)
   ```
This guarantees that clients never receive raw tracebacks or inconsistent error formats regardless of failure type.

### Q9: Why are JWT access tokens stateless, and how would you implement immediate token revocation upon logout in this architecture?
**Answer**:
Stateless JWT tokens encode user identity and claims directly into a signed payload. The server validates the token cryptographically on each request without querying a session table or cache, which provides excellent horizontal scalability.
However, because the server does not store session state, an access token remains valid until its expiration (`JWT_ACCESS_LIFETIME_MINUTES`). 
To implement logout / revocation:
1. Install `rest_framework_simplejwt.token_blacklist` in `INSTALLED_APPS`.
2. Expose a `POST /api/auth/logout/` endpoint that accepts the client's `refresh` token.
3. Call `RefreshToken(refresh_token).blacklist()`, which writes the token's unique identifier (`jti`) to a PostgreSQL blacklist table or Redis cache.
4. Any future attempt to refresh the session with that token will be rejected with HTTP 401.

### Q10: Why did we separate `MappingCreateSerializer` and `MappingReadSerializer` instead of using a single `ModelSerializer`?
**Answer**:
Using separate serializers for input and output decouples write-side validation from read-side presentation:
- **`MappingCreateSerializer`** is optimized for deserialization: it receives flat IDs (`patient_id`, `doctor_id`), runs complex business validation (verifying user ownership of the patient, doctor existence, and absence of duplicate pairs), and creates the relational record.
- **`MappingReadSerializer`** is optimized for response serialization: it projects foreign keys into rich display fields (`patient_name`, `doctor_name`, `assigned_at`) without requiring nested writable input schemas.

This separation prevents leaking internal foreign key structures and simplifies API consumption for frontend clients.
